      서명 삭제·틀린 풀이, 큐 토큰 기기 공유·샤드 클레임 변조·서명 잘라내기·만료,
      입장 토큰 탈취, 진입 경로 무상태성

**챌린지 설계 메모**

- **발급은 무상태다.** 오픈 순간 초당 수십만 건이 들어오는 경로에서 발급 1건마다
  Redis 쓰기가 생기면 관문이 스스로 병목이 된다. 챌린지에 서버 HMAC 서명을 붙여
  내려보내고, 쓰기는 풀이를 가져온 요청에만 생긴다.
- **서명이 지키는 것은 난이도다.** 서명이 없으면 클라이언트가 `difficulty=1` 로 고쳐
  되돌려 보내 PoW 전체를 무력화할 수 있다. nonce·난이도·만료·event_id 를 한 덩어리로 서명한다.
- **소각은 풀이 검증 뒤에.** 틀린 풀이에도 nonce 를 태우면 남의 nonce 를 아무 답으로
  태워 버리는 공격이 성립한다.
- **1회용 강제는 `SET NX` 한 번.** 단일 키 원자 연산이라 "먼저 도착한 하나만 성공"이
  그 자체로 보장된다. 불변식 1(Lua 단일 실행)은 큐 상태 전이에 대한 규칙이고 이건 큐가 아니다.

**봇 시뮬레이터 측정 결과** (샤드 1개, 정상 200명 + 봇 30대, 창 60초 × 30회):

| 유형 | 인원 | 최종 조치 | 누적 조치 | 최종 점수 |
|---|---|---|---|---|
| 정상 사용자 | 200 | — | 0 | 2.3 ~ 20.6 |
| naive 스크립트 | 10 | 보류 10 | 10 | 74.7 ~ 82.4 |
| heartbeat 모사 | 10 | greylist 7 | 7 | 31.7 ~ 45.0 |
| 분산 IP | 10 | greylist 10 | 10 | 61.4 ~ 66.7 |

탐지율 90% (27/30), 오탐율 0% (0/200). 사람의 최고점(20.6)과 봇의 최저점(31.7)이
겹치지 않는다 — 점수대가 분리돼야 임계값이 오탐과 미탐의 맞교환이 아니게 된다.

**heartbeat 모사 봇만 부분 탐지되는 이유** (§12 에 넣을 한계):
타이밍 위조는 공짜라 규칙성·상호상관 신호를 지운다. 남는 것은 지문(0.25)·대역(0.15)·
PoW(0.15) 뿐이고, 앞의 둘만으로는 정확히 greylist 선(40)이다. 게다가 먼저 격리된
개체는 greylist 샤드에서 비교할 모집단을 잃어 상대적 신호가 0 이 되고 점수가 내려간다.
**상대적 신호는 비교 대상이 있어야 성립한다** — 이 구조적 한계는 임계값으로 메울 수
없고, 계정·결제 수준 정책이 필요한 지점이다(§12-1).

**탐지 설계 메모**

- **판정과 적용을 나눴다.** `Scorer.Flush` 는 판정만 만들고 Redis 를 건드리지 않으며,
  상태 전이는 `Actuator` 가 Lua 로 한다. 덕분에 점수 로직을 Redis 없이 테스트할 수
  있고, "테스트가 통과하도록 임계값을 만지고 싶은" 유혹이 생기지 않는다.
- **차단만 추가 조건을 건다.** 점수가 90을 넘어도 가리킨 신호가 `MinSignalsToBlock`
  미만이면 보류로 낮춘다(`Decision.CappedFrom` 에 흔적을 남긴다). 설정 검증에서
  이 값이 2 미만이면 기동을 거부하므로, 불변식 3 은 주석이 아니라 값으로 강제된다.
- **관측되지 않은 신호는 0 이다.** "모른다"를 0.5 로 두면 근거 없이 점수가 오르고,
  그 피해는 지문을 덜 흘리는 사람이 본다. 그 결과 신호 하나만 뜨는 사용자는
  구조적으로 높은 점수에 닿지 못한다.
- **관찰만 한 건은 감사 로그를 쓰지 않는다.** 모든 사용자가 매 창마다 한 줄씩 남기면
  감사 테이블이 대기열보다 커진다.

**실제 스택을 돌려야만 나온 결함 9건** (단위·통합 테스트로는 안 잡혔다).
1~7 은 Phase 5 에서, 8~9 는 Phase 8 의 측정 중에 나왔다. **뒤로 갈수록 "무엇이
고장났는가"보다 "고장났다는 것을 어떻게 아는가"가 어려워진다** — 8·9 는 둘 다
아무것도 실패하지 않고 그럴듯한 표만 남기는 종류다:

1. **compose 가 포트를 `0.0.0.0` 에 게시** — 인증 없는 Redis 가 인터넷에 열렸고
   실제로 침해당했다. 전 포트를 `127.0.0.1` 로 묶고 Redis 인증을 켰다.
   `make check-exposure` + CI job 으로 회귀를 막는다. 경위는 그 스크립트 머리에 적었다.
2. **샤드 인덱스가 사라지면 입장이 영구히 멈춘다** — `registerShard` 의 메모가
   영구적이라, `shards:{event}` 를 잃은 뒤 다시 넣지 않았다. 대기열은 멀쩡해 보이는데
   줄만 줄지 않는 고장이다. 메모에 시한(1분)을 두어 스스로 복구하게 했다.
   (`TestShardsRegistryRecoversAfterIndexLoss`)
3. **nginx 가 백엔드 IP 를 기동 시점에 고정** — 서비스를 재생성할 때마다 502.
   `resolver` + 변수 `proxy_pass` 로 요청 시점 해석으로 바꿨다.
4. **nginx 의 `X-Real-IP $remote_addr` 가 IP 대역 신호를 통째로 무력화** —
   `httpx.ClientIP` 는 `X-Real-IP` 를 `X-Forwarded-For` 보다 **먼저** 보므로,
   흔한 관용구인 `X-Real-IP $remote_addr` 를 쓰면 조용히 그쪽이 이긴다. 그래서 전
   참가자의 `ip_prefix` 가 프록시 네트워크의 /24 하나로 접혔다. 증상이 고약한 것은
   신호가 사라지는 게 아니라 **모두에게 균일하게 만점이 얹힌다**는 점이다 — 구분에는
   전혀 기여하지 않으면서 정상 사용자 점수만 15점(가중치 0.15) 밀어올린다. 운영에서
   CDN 뒤에 두면 `$remote_addr` 는 CDN 엣지 IP 라 똑같이 무의미하다. 클라이언트 IP 에
   대한 판단은 신뢰 경계에서 하나로 정하고 두 헤더에 같이 싣는다.
5. **부하 시나리오가 지표 분모를 조용히 편향시켰다** — 인내 시간(`SG_PATIENCE`)이
   시나리오 길이보다 길면, 아직 줄을 서 있는 VU 가 `maxDuration` 에 잘려 격리 여부를
   기록하지 못한다. 분모에 남는 것은 스스로 반복을 끝낸 사람들, 즉 입장에 성공한
   사람들뿐이라 **입장 성공률이 정의상 100% 로 나온다.** 실패가 아니라 그럴듯한
   숫자로 나오기 때문에 표만 봐서는 알 수 없다. `mixed.js` 가 길이를 인내 시간에서
   유도하고, 직접 주면 예외로 막는다. 경위는 docs/REPORT.md §3 끝에 적었다.
6. **추첨 구간이 한 번도 켜진 적이 없었다** — `SG_EVENT_OPEN_AT` 이 compose 에
   아예 없어서, `enqueue.lua` 가 `lottery_end=0` 을 받아 **전원을 FIFO 밴드에
   넣고 있었다.** §3.2 의 공정성 모델(오픈 직후 도착 순서 무효화)은 봇 방어의
   1차 장치인데, §11 측정 전체가 그것이 꺼진 상태로 나온 값이다.
   단위·통합 테스트는 이걸 잡을 수 없다 — `LotteryEnd` 도 `enqueue.lua` 의
   추첨 밴드도 테스트가 있고 전부 통과한다. **빠진 것은 코드가 아니라 배포가
   그 코드에 값을 주는 일이었다.** 기능이 있고 테스트가 있고 설정 항목도 있는데
   실행 경로에 값이 닿지 않으면, 아무도 실패하지 않은 채로 기능만 꺼져 있다.
   compose 에 `SG_EVENT_OPEN_AT` 을 추가하고 왜 비우면 안 되는지 주석에 적었다.
7. **스코어러가 파티션을 0개 배정받은 채 Stable 이 됐다** — 토픽은 자동 생성이라
   **첫 produce 때** 만들어지는데, Kafka 에 볼륨이 없어 `docker compose down` 마다
   토픽이 사라진다. 스코어러가 생산자와 같이 뜨면 **없는 토픽에 조인해 파티션
   0개를 받고 그대로 안정된다.** 그 뒤 토픽이 생겨도 리밸런스할 이유가 없어
   영원히 0개다.

   이 결함이 앞의 여섯 개보다 고약한 이유는 **아무것도 실패하지 않는다**는 점이다.
   브로커 헬스체크는 통과하니 `depends_on: service_healthy` 는 초록불이고,
   컨슈머 그룹 상태도 `Stable` 이고, `ReadMessage` 는 오류 없이 그냥 블록한다.
   서비스는 전부 살아 있는데 **탐지만 통째로 꺼져 있다.** 그 상태로도 부하
   시나리오는 멀쩡히 끝나서 "탐지율 0.0% · 오탐율 0.0%" 라는 그럴듯한 표를 남긴다.
   실제로 그 표를 한 번 얻고 나서야 컨슈머 그룹의 `#PARTITIONS` 를 봤다.

   두 군데를 고쳤다. `kafka-init` 이 토픽을 미리 만들고(파티션 수 = 샤드 수 상한)
   앱 서비스는 그게 끝난 뒤에 뜬다. 코드 쪽에서는 `Consumer.waitForTopic` 이
   파티션이 생길 때까지 기다린 뒤에 조인한다. **한쪽만 두지 않은 이유는 하나면
   지워졌을 때 조용히 원상복귀하기 때문이다** — 원상복귀했다는 신호가 없는 결함이라
   더 그렇다. 회귀는 `TestComposeCreatesTopicBeforeServicesStart` 가 막는다.

8. **compose 의 환경 블록은 화이트리스트다 — 없는 이름은 조용히 무시된다** (Phase 8).
   `SG_GREYLIST_DIFFICULTY_BUMP=0` 으로 팔을 정의해 세 번 측정했는데, 그 이름이
   `deploy/docker-compose.yml` 에 없어서 컨테이너는 코드 기본값 4 로 떴다.
   export 는 성공하고 컨테이너는 정상 기동하며 시나리오도 멀쩡히 끝난다 —
   **팔만 조용히 바뀐 채로 그럴듯한 표가 나온다.** 결함 6(`SG_EVENT_OPEN_AT` 누락)과
   정확히 같은 종류이고, 같은 자리에 두 번째로 빠진 것이다.

   알아챈 경로는 설정이 아니라 결과였다: `pow_difficulty_avg` 가 10.75 였는데
   bump=0 이면 정확히 8.00 이어야 한다. 그래서 고친 것도 두 겹이다 —
   compose 에 이름을 추가하고, `cmd/gate` 가 **실제로 적용된** 난이도 설정을
   기동 로그에 찍어 `sweep.sh` 가 그 줄로 팔을 확인한다. admission 에만 있던
   검사를 게이트로 넓힌 것이다.

9. **탐지가 실행 중간에 통째로 꺼져도 시나리오는 완주한다** (Phase 8).
   한 실행이 탐지율 **0.0%** 로 끝났다. 같은 서버 설정의 다른 팔이 98.8% 였으니
   시스템이 아니라 그 실행의 문제인데, 서비스는 전부 살아 있었고 HTTP 실패율도
   0.00% 였다. 시작 전 파티션 검사(결함 7 의 산물)는 "붙었는가"만 보고,
   붙은 뒤에 이벤트가 흐르지 않으면 컨슈머는 오류 없이 블록한다.

   그래서 `sweep.sh` 가 **끝난 뒤에** 스코어러의 `botscore_actions_total` 을 세어
   0 이면 그 실행을 표에 넣지 않고 중단한다. 시작 시점의 "붙었다"와 종료 시점의
   "실제로 판정했다"는 다른 사실이고, 표를 오염시키는 것은 후자다.

**열 번째는 스택을 돌려서 나온 것이 아니다 — Phase 9 까지 `git` 저장소가 없었다.**

`.github/workflows/ci.yml` 을 쓰고, 회귀를 막는 검사를 아홉 개 넣고, 27개 팔을
측정하는 동안 **커밋은 한 건도 없었다.** CI 는 돌 곳이 없었고, 각 Phase 의 코드
상태는 남지 않았으며, 측정 결과에 "어느 코드에서 나온 값인가"를 붙일 방법이 없었다
(재현 매니페스트의 `commit` 이 `null` 인 것이 그 흔적이다).

위 아홉 개와 같은 종류다 — **아무것도 실패하지 않는다.** 빌드도 테스트도 측정도
전부 통과하고, 없다는 신호가 어디에도 뜨지 않는다. 다른 점은 도구가 아니라 절차의
결함이라 어떤 자동 검사로도 잡히지 않는다는 것이다. `git init` 은 Phase 0 에
속했어야 한다.

수리는 되돌릴 수 없다. 지나간 Phase 의 코드 상태는 존재하지 않으므로 **이력을
지어내지 않는다** — 최초 커밋 하나로 현재 트리를 넣고, 그 사실을 커밋 메시지와
여기에 적는다. Phase 경계로 쪼갠 커밋을 만들 수는 있지만 그 커밋들의 내용은
전부 최종 상태라 **그럴듯해 보이는 가짜 이력**이 된다 — 이 리포트가 1,500줄에 걸쳐
불신하는 법을 배운 바로 그 물건이다. 이력의 역할(단계적 작업의 증거)은 이 문서와
REPORT.md 가 이미 더 정확하게 하고 있다.

## Phase 8 — greylist 를 검문소로 되돌리기

**완료 기준:** 사다리가 위아래로 움직이고, REPORT.md §3.7 에 누수 채널 측정표 산출

§3.5 에서 드러난 것은 결함 하나가 아니라 세 겹이었다. 셋이 겹쳐 40~69 구간이

- [x] **점수 동결 수리** — `move_shard.lua` 의 점수 기록을 `noop` 가드보다 **앞으로**

## Phase 10 — 기준선 오염과 증거 반영 (진행 중)

§3.10~§3.12 가 남긴 두 갈래다. 하나는 탐지기의 통계적 취약점, 다른 하나는
"재검증 통과"라는 증거를 점수에 반영하지 않는 사다리의 구조 문제다.

- [x] **기준선 오염을 공격 시나리오로 명기** — DESIGN §4-L5. 상대 신호 셋(heartbeat
      상대항·상호상관·PoW)은 비교 기준을 샤드 표본에서 얻으므로, 표본의 일부를
      공급하면 기준을 옮길 수 있다. 합성으로 크기를 쟀다: 오염 12% → 50% 에서
      표적 봇의 규칙성 신호 0.780 → 0.320(REPORT §3.12).
- [x] **오염이 통하는 조건을 특정** — 절대 하한(`CVFloor`)이 살아 있으면 닿지 못한다.

      **부하가 오르면 탐지기가 오염에 열린다**(잡음 0~50ms 에서 0.000, 100ms 에서

      **전제를 먼저 쟀고, 반만 맞다**(§3.12 덤): 상호상관은 사람 0.027 / clumsy
      0.108 / 봇 0.178 이다. 사무실 집단은 짜지 않아도 같은 순간에 새로고침하므로
      깨끗한 가름선이 아니다. 게다가 **상호상관의 가중치가 0.20 이라 그 신호만으로는
      최대 20점**이고 임계는 40 이다 — 단독 신호를 전부 감쇄하면 봇도 재격리되지
      않는다. (b) 는 통과 이후의 가중치·임계 재설계와 **함께여야** 성립한다.

## 설계 문서와의 차이 (의도된 확장)

구현하며 DESIGN.md 에 반영한 항목:

1. **§3.3 Redis 키 스키마 확장** — 논리 스키마는 유지하되 Cluster 해시태그를 명시하고,
   구현에 필요한 키(`seq`, `hold`, `shards`, `entry`, `challenge`, `score`, `stats`, `suspicion`, `idem`)를
   문서에 추가했다. 태그가 없으면 한 샤드의 키들이 서로 다른 슬롯에 흩어져
   "단일 Lua 원자 실행"(불변식 1)이 Cluster 모드에서 성립하지 않는다.
2. **보류(score 70~89) 상태의 표현** — 대기열 ZSET 에 남겨 두면 순번을 점유해 뒤 사람의
   입장을 막는다. 원 순번을 그대로 보존한 채 `hold:` ZSET 으로 옮기고, 해제 시 같은
   순번으로 복귀시킨다. "대기열 유지 + admit 대상 제외"라는 의미는 그대로다.
3. **`evicting` 상태 추가** — §5 의 soft-evict 는 "미수신 3회 → 30초 유예 후 제거"다.
   유예 구간을 표현할 상태가 있어야 heartbeat 이 돌아왔을 때 순번 그대로 되살릴 수 있다.
   §3.3 의 상태 집합에 `evicting` 하나를 더했다. 소각 시각은 상태를 늘리는 대신
   `redeemed_at` 필드로 남긴다.
4. **`internal/token` 을 Phase 2 로 앞당김** — 불변식 2("토큰 검증 없이 상태를 바꾸는
   핸들러를 만들지 않는다") 때문에 Phase 2 의 HTTP 핸들러를 토큰 없이 만들 수 없다.
   JWT 발급/검증과 fp_hash·IP prefix 바인딩까지 Phase 2 에서 구현하고, Phase 3 은
   PoW 챌린지·적응형 난이도·`cmd/gate`·공격 시나리오 테스트를 맡는다.
5. **PG 18 볼륨 경로** — 데이터 디렉터리가 `/var/lib/postgresql` 아래 버전별
   하위 폴더로 바뀌었다. 예전처럼 `/var/lib/postgresql/data` 에 볼륨을 붙이면
   컨테이너가 기동을 거부한다.
6. **greylist 샤드는 원 샤드와 같은 슬롯에 둔다** — §4 의 "greylist 샤드 이동"은
   원 대기열에서 빼고 greylist 대기열에 넣고 상태를 바꾸는 세 동작이다. 두 대기열이
   다른 해시 슬롯에 있으면 Cluster 에서 한 Lua 로 묶을 수 없어 불변식 1 이 깨진다.
   그래서 `internal/keys` 의 `slotOf` 가 `g0042` 를 `s0042` 슬롯으로 접어
   `queue:{evt1:s0042}` 와 `queue:{evt1:s0042}:g0042` 를 같은 슬롯에 둔다.
   `user:` 키는 두 경우에 같은 문자열이라 사용자 해시는 이동 자체를 겪지 않는다.
7. **이벤트 전역 키는 Lua 밖에서 다룬다** — `shards:{event}` 와 `admitted:{event}` 는
   샤드 키들과 다른 해시태그를 쓰므로 Cluster 에서 샤드 Lua 안에 넣을 수 없다.
   둘 다 큐 상태 전이가 아니라 발견용 인덱스·누적 카운터이고, SADD/INCR 처럼
   그 자체로 멱등하거나 순서를 타지 않는 단일 키 연산만 쓴다. 순번·예산처럼
   원자성이 필요한 값은 전부 샤드 태그 안에 있다.
8. **admit 개시 시점을 설정으로 뺐다(`ADMIT_AFTER_LOTTERY`)** — §3.4 원안은 배분
   **비율**만 정하고 개시 **시점**은 말하지 않는다. §12-7 에서 그 시점이 탐지율의
   상한을 정한다는 것이 드러났으므로, 추첨 구간 종료까지 admit 을 닫는 선택지를
   DESIGN.md §3.4 에 추가했다. 공정성이 아니라 처리량과 탐지율의 맞교환이라
   기본값은 꺼 둔다.
